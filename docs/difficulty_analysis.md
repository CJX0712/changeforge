# DGP 难度标定分析

> 本文回答一个问题：**ChangeForge 的五档难度梯度，是真单调的吗？**
> 结论是**不完全单调**，我们把导致倒挂的三个机制逐个定位、修掉两个、
> 剩下一个如实记录为开放问题。数据全部来自 `scripts/difficulty_probe.py`
> 的真实重跑（每档 20 条序列 × 6 个快检测器），无手工估算。

一键复现：

```bash
python scripts/difficulty_probe.py --n 20 --tol-fixed 10
# -> artifacts/difficulty_probe.json
```

---

## 1 · 问题：难度倒挂

quick 基准首轮结果（每档仅 1~2 条序列）显示：

| 档位 | 名义难度 | 实测 macro-F1（6 快检测器） |
|---|---|---|
| D0 Smoke | 最易 | 1.00 |
| D3 Medium | 中 | 0.44 |
| D4 Hard | 难 | 0.50 |
| D5 Expert | 最难 | **0.82** |

D5 "Expert" 明显好过 D3 "Medium"，梯度是反的。

**第一步是排除采样噪声**：D3/D4/D5 原来只跑 1~2 条序列，单点估计没有统计意义。
把每档提到 20 条后：

| 档位 | 20 条序列 macro-F1 @ tol=0.01n |
|---|---|
| D3 | 0.131 |
| D4 | 0.123 |
| D5 | 0.422 |

倒挂**依然存在**，所以这不是噪声，是真问题。

## 2 · 机制 A：容差口径与变点数耦合（已修复）

`tol = 0.01 * n` 是行业常见口径，但它隐含一个陷阱——
平均段长 ≈ `n / K`，于是：

```
tol / 平均段长 = 0.01 * n / (n / K) = 0.01 * K
```

**容差相对段长的比例正比于变点数**。实测：

| 档位 | K | 平均段长 | tol | tol/段长 |
|---|---|---|---|---|
| D0 | 1 | 500 | 10 | 0.02 |
| D3 | 4 | 200 | 10 | 0.05 |
| D4 | 8 | 111 | 10 | 0.09 |
| D5 | 20 | 95 | 20 | **0.21** |

D5 的容差覆盖 42% 的序列位置（±20 / 间隔 95），随机报点都有可观命中面；
D3 只覆盖 10%。**在口径 A 下跨档比 F1 本身就不公平。**

**修复**：新增口径 C，`tol = 0.1 * n / (K_true + 1)`，使 `tol/段长` 恒为 0.1。

| 档位 | 口径 A (tol=0.01n) | 口径 C (tol=0.1·段长) |
|---|---|---|
| D3 | 0.131 | 0.191 |
| D4 | 0.123 | 0.131 |
| D5 | 0.422 | 0.388 |

口径 C 下 **D3 > D4 恢复单调**。基准与报告现同时输出两个口径。

> 代价说明：口径 C 用到了真值 K 的弱先验（而非位置信息），
> 属评测协议的一部分，与 oracle-K 参考一样需明确标注，不进主表对比。

## 3 · 机制 B：均值变化按全局最短段反解（已修复）

原实现：

```python
m_min_eff = min(e - s for s, e in segments)
state_mu += detectability_delta(n, m_min_eff, d_target) * state_sd
```

可检测性指数 `D = kappa - sqrt(2·log(n/m_min))` 里的 `m_min` 用的是**全局最短段**。
对段长均匀的 D3 没问题，但 D5 段长在 20~几百之间随机：

- 按最短段 20 标定 → `Δμ/σ = (0.4 + 3.03) × 0.316 = 1.084`
- 但平均段长是 95，实际 `kappa = 1.084 / sqrt(2/95) = 7.47`
- 实际 `D_actual = 7.47 - sqrt(2·log(2000/95)) = 7.47 - 2.47 ≈ 5.0`

**名义 D_target = 0.4（最难），实际 D ≈ 5.0（很容易）**，比 D3 的 1.7 还容易 3 倍。

**修复**：新增 `detectability_delta_pair(n, m1, m2, d_target)`，
按相邻两段的**实际长度对**逐边界反解，每个边界都精确落在 D_target 上。

```python
m_prev = segments[j - 1][1] - segments[j - 1][0]
state_mu += detectability_delta_pair(n, m_prev, m_cur, spec.d_target) * state_sd
```

## 4 · 机制 C：方差变化累积放大（已修复）

原实现 `state_sd *= 1.6` 是**连乘**：变化类型轮转表里 var 出现 K/4 次，
于是 K 越大，末段方差越大。

- D4 (K=8)：2 次 var → `sd = 1.6² = 2.56`
- D5 (K=20)：5 次 var → `sd = 1.6⁵ = 10.5`

**变点越多、信号越强**——这与"更难"的设计意图完全相反。

**修复**：改交替不累积（`1.35 ↔ 1.0`），AR 强度同步弱化（`0.40 ↔ 0.15`），
使非均值变化的固有强度不随 K 增长。

## 5 · 剩余开放问题：D5 仍然倒挂

口径 C 下的最终状态：

```
D0 0.788  >  D3 0.191  >  D4 0.131   ✅ 单调
                              D5 0.388  ❌ 反弹
```

D3→D4 已修复，D5 仍高于两者。**这不是误报灌水**——我们专门验证了：

| 档位 | 检测器 | Precision | Recall | 预测数 / 真值 K |
|---|---|---|---|---|
| D3 | numpy-pelt-l2 | 0.42 | 0.21 | 2 / 4 |
| D4 | numpy-pelt-l2 | 0.22 | 0.23 | 9 / 8 |
| D5 | numpy-pelt-l2 | 0.59 | 0.55 | 19 / 20 |
| D5 | numpy-binseg-l2 | **0.80** | 0.55 | 14 / 20 |
| D5 | numpy-window-l2 | 0.73 | 0.66 | 19 / 20 |

D5 的 precision 高达 0.59~0.80、预测数逼近真值——检测器是**真检到了**，
不是靠乱报凑中。

### 我们的判断

D5 (n=2000, K=20) 的密集变点 + AR(0.6) 自相关 + t(3) 重尾 + 3% 离群，
制造了大量局部结构。对 l2 类代价而言：

1. 真值密集意味着**任何定位误差的绝对代价都更小**，段内 SSE 惩罚天然偏低；
2. 固定的 PELT 惩罚 `β = λ·d·σ̂²·log n` 相对这些局部结构显得不足，
   分割点更容易被接受；
3. 归一化容差后 tol=10 相对段长 95 仍有 10% 宽松度，比 D3 的命中面更大。

三者叠加，使"变点密集"在现有评测协议下反而是**送分**而非加分。

### 未采纳的修法及原因

| 尝试 | 结果 | 为何不采纳 |
|---|---|---|
| 把 D3 也改成混合变化类型 | D3 从 0.191 **跌到 0.077** | l2 代价看不见方差变化，混合档对 l2 而言可检边界更少，F1 被稀释 |
| 继续调低 D5 的 d_target | D5 仅 0.422→0.388，无实质改善 | 主因不是信噪比，是评测协议与局部结构 |
| 拉长 D5 段长（降 K） | 未实施 | 会失去"密集变点"这一设计意图，且 n 增大使 constab 基准耗时翻数倍 |

**这就是一个真实的开放问题，不做美化。** 若后续要解决，方向是改评测协议
（如用 Hausdorff / 覆盖型指标替代容差匹配 F1），而非继续调 DGP 参数。

### 修复后基准确认（quick 重跑，macro F1@口径C）

```
D0 0.896 / D3 0.320 > D4 0.177   ✅ D3→D4 单调保持
                       D5 0.361   ⚠️ 仍高于 D4，与探针结论一致
```

`artifacts/benchmark.json` 现同时输出 `f1_mean`（口径 A）与 `f1_mean_norm`（口径 C）
两套字段，`docs/benchmark_report.html` 含 1C 对照表。

## 6 · 实验记录：一次被数据推翻的假设

值得记一笔的过程：我们最初假设"D5 高 F1 是 AR 噪声导致误报、恰好撞上密集真值"。
跑了 precision/recall 分解后**假设被否**——precision 0.59~0.80 说明是真检出。
随后才定位到"变点密集使定位代价变小"这一真正的机制。

**教训：先分解指标再改参数。** 单次 F1 聚合值会掩盖 precision/recall 的相反走向。
